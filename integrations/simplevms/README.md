# Native SimpleVMS integration

SimpleVMS owns cameras, names, profiles, recording policies and display-group membership. BetterFrame owns layouts authored by operators and the list of kiosks permitted to use each recorder. No camera/recording configuration is pushed from BetterFrame to SimpleVMS. MediaMTX is not part of this integration.

Each snapshot is limited to 4,096 playable cameras, 32 supported profiles per camera, and 4 MiB of JSON. Oversized catalogs export a stable prefix in camera-ID order that fits both limits; groups reference only those exported cameras. The native plugin logs a warning when cameras are omitted because of unsupported profiles or catalog limits. Omitted cameras are unavailable in BF until they fit in the exported catalog.

## Build and install

Build against **the same extended SimpleVMS source used by the target recorder**. The host must expose `PluginContext.CameraRegistry`, `EventBus`, `StreamTap` and the native H.264/H.265 format contracts. Browser media uses that source tree's Fmp4 muxer; recording export also requires `RecordingAccess` and `ffmpeg` on the recorder. This is not a claim of compatibility with an unmodified upstream release.

```sh
bash integrations/simplevms/build.sh /absolute/path/to/extended/simple-vms /tmp/bf-vms-package
```

The build script copies the host into an isolated temporary directory and applies `host-pairing/browser-pairing.patch`; it never edits the source checkout. It produces `plugin/`, matching `host/Shared.Models.dll` and `host/Server.Api.dll`, and `host/wwwroot/`. Deploy these together using the recorder's normal deployment process, then enable the plugin. Installing only the plugin DLL does not add the native Pair button or its guarded endpoints. The optional overlay Dockerfile consumes this package directory. Keep the recorder's existing data volume and single writer. Do not replace or initialize its databases.

The companion host change exposes only BetterFrame pairing begin/complete operations, guarded by same-origin JSON requests and the existing plugin-configuration write permission. A host with no authentication provider permits these operations only from loopback; use its local browser or an authenticated native admin deployment. Reverse proxies must preserve the correct request origin through the host's trusted forwarding configuration. The public return document only performs a same-origin navigation; it cannot change settings or redeem pairing grants.

For a patched build checkout, run `dotnet test integrations/simplevms/BetterFrame.Tests/BetterFrame.Tests.csproj -p:SimpleVmsSource=/path/to/patched-host` and `dotnet test integrations/simplevms/Host.Tests/Host.Tests.csproj -p:SimpleVmsSource=/path/to/patched-host`. The standalone host tests avoid the upstream desktop client's unrelated private FFmpeg package.

An optional Chromium regression uses the built native web UI, real BF routes and a native API test double. Set `BF_TEST_PG_URL` to disposable PostgreSQL, `BF_PAIRING_NATIVE_WEB_ROOT` to the patched `Client.Web/dist`, and `BF_PAIRING_PLAYWRIGHT_MODULE` to an installed Playwright module, then run `TSX_TSCONFIG_PATH=server/tsconfig.test.json node --import tsx server/tests/simple-vms-pairing.browser.ts`. It covers the actual Pair button, cross-site Strict cookies, BF confirmation, credential redemption, first sync and kiosk selection. Native protocol/persistence and endpoint authorization are tested separately in .NET.

The native test suite requires `ffmpeg` (with `libx264`) and `ffprobe` on `PATH` for its generated-video recording-export regression. No camera footage is used.

Recording export copies encoded video. Start boundaries retain the preceding keyframe as decoder preroll, so cuts follow keyframe boundaries rather than arbitrary frames; see [FFmpeg's input-seeking behavior](https://ffmpeg.org/ffmpeg.html#Main-options).

## Configure

1. In SimpleVMS **Settings → Plugins → BetterFrame**, enter a recorder name and the HTTPS BetterFrame server URL, then choose **Pair with BetterFrame**. Enable the plugin first if it is stopped.
2. Sign in to BF if needed and approve the recorder in the intended tenant. The browser returns to SimpleVMS to complete the connection, then opens its BF instance page. Integration tokens, reader usernames/passwords and callback URLs are generated and exchanged automatically. Pairing codes expire after ten minutes and require the native recorder's private PKCE verifier. Persistent credentials never appear in browser redirects.
3. BF now imports the NVR and child cameras immediately, without requiring an owning kiosk. Camera lifecycle events and group changes subsequently trigger snapshots; healthy operation does not poll the catalog. Failed delivery retries the durable outbox. A newer complete snapshot can replace an unsent older snapshot without losing deletions. **SimpleVMS instances** lists all paired regional/property recorders independently.
4. Open a kiosk's settings, select a paired **SimpleVMS instance** and choose **Connect instance**. If the recorder runs on that kiosk, select **SimpleVMS runs on this kiosk**; otherwise it needs a reachable media address. A kiosk may connect to multiple instances. Their generated layouts attach automatically, and disconnecting one instance preserves access to the others. Android viewers use network recorder addresses and retain assigned-camera scope.
5. Create named **Display groups** in the SimpleVMS plugin settings. Each camera's BetterFrame settings expose membership toggles. Renames retain stable group IDs. Groups do not change recording policies. Ungrouped cameras are imported too, for custom BF layouts.

The persistent instance ID, event outbox, reader grants and private `connection.json` live under the recorder's `betterframe/` data directory; preserve them on upgrades and backups. Re-pairing rotates credentials while preserving BF source/camera/layout IDs and kiosk associations. Existing manually connected sources migrate to independent instances and retain their local kiosk links. No credentials need to be copied during migration. BF and native read-only landing pages preserve Strict session cookies across cross-site navigation; login and two-factor continuation retain the pending pairing request.

The RTSP listener defaults to `127.0.0.1:8554` and supports H.264/H.265 over interleaved TCP. Configure a private bind address for remote kiosks. For RTSPS, configure the certificate/key PEM paths and use `rtsps://` in BF. The browser media listener defaults to `http://127.0.0.1:8555`. Remote browser media requires HTTPS, using the configured certificate or a private HTTPS reverse proxy. Kiosks must trust the issuer; certificate verification remains enabled.

Managed images allow TCP 8554 and 8555 only from private/link-local IPv4 and IPv6 networks. When changing native listener or reverse-proxy ports, update `/etc/nftables.conf` to allow those ports for the same trusted source networks, then reload it with `sudo nft -f /etc/nftables.conf`. Binding a listener and configuring its external BF address do not change the firewall automatically.

Each local kiosk can use its own localhost recorder address; SimpleVMS identity is scoped by instance, not by that local endpoint. Use **Disconnect** in kiosk settings to remove that kiosk's access without deleting the recorder. Use **Remove instance** on the BF instance page to atomically remove its imported NVR/cameras/generated layouts while preserving custom layouts. Deleting a kiosk leaves independently paired recorders intact. None of these operations deletes native cameras, recording policies or recorder history.

Native camera labels are retained where unique in BF. Duplicate labels are qualified by recorder name, with an external-reference suffix only when still ambiguous. Renames and name swaps retain camera IDs and layout references.

When the recorder uses the ControlRoom policy plugin, configure its service URL/key in the BetterFrame plugin. Missing policy configuration on a recorder with an existing ControlRoom policy database fails closed. Incident-only `alarm_review` cameras are excluded from ordinary exports. This integration does not issue incident grants or change incident/evidence policy.

## Synchronization and access

- Tenant-local mappings use instance/camera/group external IDs. Camera and group renames preserve BF IDs and assignments. No upstream camera address or password enters the catalog or BF bundle.
- Each snapshot is validated and applied in one transaction, serialized per recorder. Duplicate/older revisions are acknowledged without applying them. A network failure never implies deletion. Snapshot requests have a 4 MiB limit.
- Imported NVRs/cameras and generated layouts are read-only in BF; repository guards also reject direct mutation requests. An empty/deleted group removes its generated layout and clears default-layout references. Camera deletion uses the existing cleanup for custom layouts and leaves those layouts intact.
- The kiosk catalog includes imported cameras before layout assignment. The NVR/camera/layout pages show connected kiosks. Source presence is separate from successful camera playback: no camera-health claim is inferred from a catalog entry.
- BF distributes separate derived reader credentials per kiosk and camera. The plugin checks the kiosk's current connection authorization with BF at connection time and during streaming (approximately every ten seconds). Linked Android viewers retain their assigned-camera scope; ungrouped cameras remain available to native desktop kiosks for custom layouts. Disabling a source or disconnecting a kiosk withdraws access as well as generated assignments while BF is reachable. These checks are not camera-catalog polling.
- A private, durable cache retains the last known reader grants across recorder restarts and BF outages. Catalog acknowledgements seed authorized scopes, and successful reader checks update individual grants/denials. Previously authorized cameras remain playable while BF is unavailable; unknown readers remain denied. Explicit denials are retained. BF changes made during an outage take effect once connectivity returns. Camera policy checks remain local to SimpleVMS/ControlRoom.
- Each RTSP viewer owns a native StreamTap subscription, disposed on teardown/disconnect. Slow writes time out. Recording and other native consumers retain their own demand. Browser live preview remuxes native frames to fMP4 without transcoding. Recording export prefers the requested profile, then tries other authorized supported profiles for complete coverage; it never splices different profiles or missing periods together. It remuxes up to ten minutes of native segments, reports missing coverage, limits temporary data, and cleans up on cancellation.

## Migration and validation

The old BF camera recording JSON editor, MediaMTX recording synchronization, WebRTC gateway and bundled gateway installation are removed. The standalone installer retires an existing gateway service after the new app confirms healthy startup, while retaining its recordings and configuration. Until then, the legacy service stays available for binary rollback, including deferred desktop startup. For a deferred installation, rerun setup after the app starts successfully to retire that service; native BF does not use it. Existing MediaMTX files are **not** converted into native SimpleVMS history. Before running that migration on a recorder, retain/export old history and qualify the native recording/playback path. Do not claim historical cutover from a successful catalog sync.

Run the server suite with `BF_TEST_PG_URL` set to a disposable PostgreSQL administrator connection; tests create and remove isolated databases. Native plugin tests cover catalog generation, grouping controls, durable delivery/retries, lack of healthy catalog polling, RTP fragmentation, authentication and subscription cleanup. The regular client CI compiles the Rust changes. Physical-kiosk acceptance still requires actual H.264/H.265 playback, hot/warm/cold transitions, reconnects and profile changes, continued recording during viewer changes, linked-kiosk reachability and certificate trust, and browser playback/export against native recordings.
